데이터 흐름 시각화 (Sankey Diagram)

시스템 내에서 발생하는 트래픽의 이동 경로입니다. 아래 버튼을 클릭하여 사용자 요청(User Traffic), 로그 수집(Logging), 메트릭 수집(Metrics)의 흐름을 전환하며 확인하세요.

서비스 요청 흐름 (User Traffic)

  1. User → Cloud LB (HTTPS Termination)
  2. Cloud LB → Nginx (Vue.js 정적 응답 / API Proxy)
  3. Nginx → APISIX (API 라우팅 및 인증)
  4. APISIX → Spring Boot (비즈니스 로직 수행)

본 아키텍처를 수립하기 위해 내려진 핵심 기술적 의사결정과 그 근거입니다. 보안성과 운영 효율성을 최우선으로 고려하였습니다.

🐳

Frontend Docker 컨테이너화

  • 결정: Public Subnet의 VM에 Nginx를 직접 설치하지 않고 Docker로 배포.
  • 근거: Backend와 배포 파이프라인 통일, 웹 서버 탈취 시 호스트 OS 보호(격리), 롤백 용이성.
🐝

Docker Swarm 오케스트레이션

  • 결정: Backend 시스템은 Docker Swarm 클러스터링 적용.
  • 근거: Kubernetes 대비 낮은 구축/운영 복잡도, 서비스 디스커버리 및 오토 스케일링 기본 제공.
💾

Stateful 서비스의 분리

  • 결정: Kafka, OpenSearch 등은 Swarm 외부 또는 관리형 서비스 사용.
  • 근거: 데이터 유실 방지 및 I/O 성능 보장, Stateless 컨테이너 환경의 안정성 확보.
🔒

서브넷 분리 원칙

  • 결정: Public(DMZ)과 Private(App) 망의 엄격한 분리.
  • 근거: Private Zone은 외부 직접 접속 불가(NAT 사용), Inbound 트래픽은 오직 Public Nginx에서만 허용.
